# i18n Workflow

The project uses [i18next](https://www.i18next.com/) with the
[react-i18next integration](https://react.i18next.com/). Since the TanStack Start migration the app
renders on the server too, so there are three entry points instead of one.

## Files

| File                                                                                           | Runs on              | Purpose                                                                                                                                 |
| ---------------------------------------------------------------------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| [features/i18n/i18n.config.ts](apps/platform/features/i18n/i18n.config.ts)                     | both                 | Namespaces, supported languages, language resolution, CDN URLs. Single source of truth.                                                 |
| [features/i18n/i18n.ts](apps/platform/features/i18n/i18n.ts)                                   | client (+ SSR proxy) | Client `init()` (guarded by `!import.meta.env.SSR`); on the server it proxies to the per-request instance. Exports `t`, `default i18n`. |
| [features/i18n/i18n.server.ts](apps/platform/features/i18n/i18n.server.ts)                     | server               | Per-request instance, reads locale JSON from disk, detects language from cookie / `Accept-Language`.                                    |
| [features/i18n/I18nSSRProvider.tsx](apps/platform/features/i18n/I18nSSRProvider.tsx)           | both                 | Wraps the tree in `I18nextProvider`; on the server builds an instance from the request state, in the browser reuses the global one.     |
| [features/i18n/i18n.dehydrated-state.ts](apps/platform/features/i18n/i18n.dehydrated-state.ts) | client               | Reads the SSR payload so the client init starts already hydrated (`partialBundledLanguages: true`).                                     |

## Debug

Set `VITE_I18N_DEBUG=true` in `.env` to get i18next logs in the console.

## Namespaces

Defined in `i18n.config.ts`:

- `SERVER_NAMESPACES` — `translations`, `workspaces`, `help-hints`, `layer-library`. Shipped in
  `public/locales/`, read from disk on the server, HTTP-loaded on the client via
  [i18next-http-backend](https://github.com/i18next/i18next-http-backend).
- `PACKAGE_NAMESPACES` — `flags`, `timebar`. **Client-only**, fetched from the CDN. They are absent
  during SSR, so anything relying on them renders untranslated (raw key) on the server pass.
- `CLIENT_NAMESPACES` = both. `DEFAULT_NAMESPACE` is `translations`.

To use a non-default namespace, prefix the key (e.g. `flags:ESP` in `I18nFlag`).

## Translations

Source and translated files live in
[public/locales](apps/platform/public/locales) — one folder per language (`en`, `es`, `fr`, `id`,
`pt`, plus `source` and `val`).

- `source` — the extraction target, what Crowdin reads.
- `val` — Crowdin in-context pseudo-language. `source` and `val` are only added to
  `SUPPORTED_LANGUAGES` in development (and never under Vitest).

Translation management is [Crowdin](https://crowdin.com/project/gfw-frontend). A GitHub bot watches
the source files and opens a PR with the translations once editors approve them. **Developers only
edit `public/locales/source/<namespace>.json`** — never the per-language files.

Shared labels (datasets, flags, timebar) live in the
[i18n-labels](libs/i18n-labels) lib (note: moved from `packages/` to `libs/`), published to npm and
consumed over jsdelivr:

```text
https://cdn.jsdelivr.net/npm/@globalfishingwatch/i18n-labels@{stable|latest}/{{lng}}/{{ns}}.json
```

`SHARED_LABELS_PATH` picks the tag from `WORKSPACE_ENV` (`stable` in production, `latest`
elsewhere), and in development serves from `http://localhost:8000` instead — that is the
`i18n-labels:serve` target (an `@nx/web:file-server` over `libs/i18n-labels`), which the platform
`start` target depends on. URLs are cache-busted with `?v=__BUILD_ID__`.

To purge a hotfix from the CDN cache:

```text
https://purge.jsdelivr.net/npm/@globalfishingwatch/i18n-labels@stable/{{lng}}/{{ns}}.json
```

or run [libs/i18n-labels/purge_jsdelivr.sh](libs/i18n-labels/purge_jsdelivr.sh) with `PACKAGE_TAG`
set, which purges every language/namespace pair.

## Language detection

Server and client resolve the language the same way (`resolveLanguageFromSources` /
`CLIENT_LANGUAGE_DETECTION`):

1. `i18next` cookie
2. `Accept-Language` header (server) / `navigator` (client)
3. `<html lang>` (client only)
4. `FALLBACK_LNG` (`en`)

The cookie is written on change (`caches: ['cookie', 'localStorage']`, path `/`, `sameSite: lax`).
`toDocumentLang()` maps the dev-only `source`/`val` codes to `en` for a valid `<html lang>`.

## Key extraction + TypeScript definitions

Extraction moved from `i18next-parser` to
[i18next-cli](https://github.com/i18next/i18next-cli), configured in
[i18next.config.ts](apps/platform/i18next.config.ts). It scans `data`, `features`, `hooks`, `pages`,
`routes`, `router`, `server`, `types`, `utils` and writes
`public/locales/{{language}}/{{namespace}}.json`.

```bash
nx i18n platform          # extract + types
nx i18n:extract platform
nx i18n:types platform
nx i18n:watch platform    # continuous
pnpm --filter @gfw/platform i18n:status
```

`i18n` / `i18n:types` are `dependsOn` of the build and typecheck targets, so CI regenerates them.
They are **not** part of the lint-staged pre-commit hook — that only runs `eslint --fix` and
prettier/stylelint.

Type generation (`types` block in `i18next.config.ts`) emits:

- `features/i18n/i18next.d.ts` — module augmentation
- `features/i18n/i18n.types.d.ts` — the resource types

`enableSelector: 'optimize'` turns on the **typed selector API**, which is what the codebase uses:

```ts
t((t) => t.common.share)
t((t) => t.vessel.share)
```

Dynamic keys can't be statically extracted. Two mechanisms cover them:

- `extract.preservePatterns` in `i18next.config.ts` — keeps API-driven trees
  (`datasetUpload.errors.*`, `vesselGroupReport.insights.*`, `vessel.gearTypes.*`,
  `vessel.vesselTypes.*`) and hand-managed namespaces (`layer-library:*`, `workspaces:*`).
- [features/i18n/translations/translation.keys.ts](apps/platform/features/i18n/translations/translation.keys.ts)
  and [many.keys.ts](apps/platform/features/i18n/translations/many.keys.ts) — comment-only files
  listing `// t('vessel.flag')`-style keys so the extractor sees them
  ([upstream caveat](https://github.com/i18next/i18next-parser#caveats)).

Note that a dynamic key whose variable has a **string-literal union type** _is_ resolved —
`expression-resolver.ts` expands the union. `t((t) => t.common[activityUnit], { count })` in
[ReportSummaryActivity.tsx](apps/platform/features/_reports/shared/summary/ReportSummaryActivity.tsx)
therefore emits plural forms for all four members of `ReportActivityUnit`
(`hour | detection | numEvents | coverage`), including the ones that read oddly as plurals.

## Why the i18n targets pin `LC_ALL=en_US.UTF-8`

`locales: ['source']` is fed straight to `new Intl.PluralRules('source')` so Intl silently
falls back to the **machine's system locale**. On an `es`/`pt` machine that locale has a `many`
plural category, so the extractor writes `key_many` entries that English never selects.

## Datasets translations workflow

- Dataset sources come from `datasets-versioning` published in PROD with `translate: true`.
- Sources and translations land in `develop` through pull requests.
- On push to `develop` touching `libs/i18n-labels/**` (excluding its `package.json`),
  [.github/workflows/libs-release.yml](.github/workflows/libs-release.yml) bumps the version,
  publishes to npm as `@latest`, and purges the jsdelivr cache. This replaced the old
  `i18n-labels-publish.yml`.
- On a `@gfw/platform@*` tag (i.e. a platform production release),
  [.github/workflows/i18n-labels-stable.yml](.github/workflows/i18n-labels-stable.yml) moves the
  `stable` dist-tag to whatever `latest` points at, then purges the cache. So production apps read
  `@stable` and development apps read `@latest`.
